# Shirakami Licensing — Legal Review Checklist

## Status

Pre-legal checklist. Not legal advice and not a substitute for counsel.

## 1. Rights inventory

- [ ] Identify every file/directory intended to remain under the current implementation license.
- [ ] Identify normative protocol specifications intended for a future protocol license.
- [ ] Identify generated files and determine their licensing basis.
- [ ] Identify contributor-owned or third-party material.
- [ ] Preserve required copyright, attribution, and dependency notices.
- [ ] Check whether any dependency license imposes conditions on redistribution or modification.

## 2. Compatibility

- [ ] Determine whether the proposed Protocol License is compatible with the licenses of referenced or incorporated materials.
- [ ] Determine whether existing MIT-licensed code remains independently distributable after the protocol transition.
- [ ] Document migration treatment for existing releases and copies.
- [ ] Define which license governs each new file added after adoption.

## 3. Protocol terms

- [ ] Define the exact scope of “normative protocol material.”
- [ ] Define permitted study, implementation, testing, modification, and commercial integration.
- [ ] Define how protocol versions and license versions interact.
- [ ] Define treatment of derivative protocol specifications.
- [ ] Define termination and cure provisions, if any.
- [ ] Define warranty and liability language through qualified counsel.

## 4. Commercial integration

- [ ] Define objective vendor eligibility conditions.
- [ ] Define pricing and whether pricing is uniform, tiered, or otherwise objectively determined.
- [ ] Define API/SDK/hosted-service rights separately where needed.
- [ ] Define security, incident reporting, data handling, and audit obligations.
- [ ] Avoid accidental exclusivity unless separately and deliberately negotiated.
- [ ] Define jurisdiction, dispute resolution, and termination through counsel.

## 5. Conformance and branding

- [ ] Define observable conformance requirements and version them.
- [ ] Separate conformance from source-code similarity.
- [ ] Define who may issue a conformance determination.
- [ ] Define permitted use of the Shirakami name, logo, badges, and “conformant” wording.
- [ ] Review trademark and unfair-competition implications.
- [ ] State clearly that repository tests are evidence, not automatic external certification.

## 6. Authority boundary

- [ ] Confirm that no license term grants an AI system decision authority.
- [ ] Confirm that API credentials do not imply execution, publication, merge, or decision authority.
- [ ] Confirm that Evidence IDs, verification results, or conformance status cannot be interpreted as authorization.
- [ ] Preserve Human Gate requirements in protocol and commercial documents.

## 7. Adoption gate

- [ ] Legal review completed and documented.
- [ ] Final texts versioned.
- [ ] Migration/compatibility notes prepared.
- [ ] Human Gate explicitly approves adoption.
- [ ] Only then change the repository top-level LICENSE or publish binding vendor terms.
