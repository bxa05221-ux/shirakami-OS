# 白神OSは、どうやって生まれたのか

## 開発者の話

> **元牧師で、付属保育園の園長、教誨師を経て、現在は障害者就労支援事業所を経営している、田舎のおじさん。**
>
> **56歳のとき、2025年6月、小説を書くためにAIを使い始めた。**
>
> **気がついたら、プロトコルを生成するためのメタプロトコルである「白神モデル」を作っていた。**
>
> **調子に乗ってGitHubと連携し、今ではOSまで作っている。**

これは、普通のAI研究者の経歴紹介ではない。

そもそも開発者は、AIエンジニアとして始めたわけではない。

重要なのは、AIとの対話が、いつの間にか開発環境そのものになっていった過程である。

## 小説からプロトコル開発へ

出発点は創作だった。小説を書くためにAIを使い始めた。

その過程で、別の問題が見えてきた。

AIは会話を処理できる。しかし、人間が積み重ねてきた文脈、視点、会話状態、意図を、AIやモデルが変わってもどう継承するのか。

そこで、それらの関係を明示する方法としてプロトコルが使われ始めた。

白神モデルは認知観測の枠組みとして発展し、的目YAMLは、プロトコルをRuntimeへ引き渡すための正式な形式として位置づけられた。

## プロトコルからGitHubへ

次の段階は、単にコードをGitHubへ保存することではなかった。

GitHubそのものが開発ループの一部になっていった。

```text
人間の問い
      ↓
AIとの対話
      ↓
プロトコル / 的目YAML
      ↓
実装
      ↓
GitHub
      ↓
テスト / PR / Commit
      ↓
Evidence
      ↓
Architectureの修正
      ↓
再びAIとの対話
```

Repositoryは、仕様、実験、実装、テスト、レビュー、履歴を接続して保持する、外部のDevelopment Landscapeになった。

## ちょっと変なところ

開発者は、最初からAI用OSを作ろうとしていたわけではない。

問い、実装、観測、批判、検証、再設計を繰り返すうちに、Architectureそのものが変化していった。

外部AIはレビュアーや開発参加者として利用される。しかし、その提案をそのまま正解とはしない。

AIからの指摘はObservationとして扱い、必要ならExperimentへ変換して検証する。

重要なのは、次の区別である。

> **AIがArchitectureを所有するのではない。EvidenceがArchitectureを更新する。**

## なぜ、この経緯を残すのか

Shirakami OSは、AIインフラを別の方法で作れるかを試す実験でもある。

中心にある問いは、

> より高性能なAIモデルをどう作るか？

ではない。

> **AIが変わっても、人間は自分のLandscapeをどう保持できるのか？**

である。

そして、その問いを考えている開発過程そのものも、実験の一部になっている。

人間の経験、AIとの対話、プロトコル、Repository、テスト、Evidenceを、ひとつの変化し続けるLandscapeとして扱っている。

## 現在

現在のプロジェクトは、創作のためのAI利用から始まり、次の領域を扱うオープンソースの実験へと成長している。

- Human Landscapeの保存
- Protocol駆動型AI Runtime
- Personal AI Runtime Architecture
- Evidence-driven Development
- Runtime Boundary
- Modelに依存しないContext Continuity
- AIとGitHubを組み合わせた開発環境

この物語は、まだ続いている。
