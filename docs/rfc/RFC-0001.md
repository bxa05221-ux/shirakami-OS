# RFC-0001: Protocol Contract (Architecture Root for Adapters)

Status: Draft

Date: 2026-08-02

Authors: Atsushi Chiba

Protocol Owner: Shirakami OS Project

Reviewers: 

## Purpose

This RFC defines the Protocol Contract layer for Shirakami OS. The Protocol Contract is the abstract, runtime-independent specification that establishes the semantic and behavioral contract which all adapters and protocol implementations must derive from. It is the authoritative source of meaning for operations, state transitions, error semantics, conformance expectations, and high-level versioning rules. Protocol Contract is intentionally implementation-agnostic: it describes observable behavior and obligations, not code or APIs.

## Scope

This document establishes:

- The role of a Protocol Contract in the architecture pipeline.
- The responsibilities and boundaries between Protocol Contract and Adapter_Base.
- The kinds of semantics and artifacts a Protocol Contract must define (meaning, lifecycle, conformance criteria, extension model, high-level security requirements, versioning principles).
- The required downstream artifacts that Protocol Contract decisions enable (Adapter_Base updates, adapter-level specs, conformance specifications, governance artifacts).

This RFC does not:

- Specify language, runtime, API formats, or implementation details.
- Provide concrete, machine-readable schemas or test code (those are created in downstream specs after Protocol decisions).

## Principles

All Protocol Contracts created under this RFC SHALL follow these principles:

- Implementation Independence: Contracts describe observable behavior and meaning; they do not prescribe implementation choices.
- Semantics First: Define the meaning of operations, state transitions, and error conditions before defining structural representations.
- Verifiability: Provide unambiguous, testable conformance criteria at the protocol level (not test code itself).
- Stability and Versioning: Changes to Protocol Contracts must follow the project's governance and versioning policy; breaking changes must be explicitly called out and managed.
- Extension Points: Protocols MUST declare supported extension points and their compatibility guarantees.
- Security by Contract: Protocols MUST document trust boundaries and high-level security obligations; specifics of credential storage remain adapter/runtime concerns.

## Protocol Contract: Definition and Responsibilities

A Protocol Contract is a document (and associated decision record) that SHALL include, at minimum, the following sections:

1. Intent and Motivation — what this protocol models and why it exists.
2. Domain Vocabulary — canonical terms and their meanings (reference Glossary).
3. Abstract Operations and Commands — semantic description of actions the protocol supports.
4. State and Lifecycle Model — abstract state machine(s) describing valid states and transitions for protocol subjects.
5. Error Taxonomy and Expected Recovery Semantics — categories of failures and allowed response behaviors (retry, abort, compensating action). 
6. Conformance Criteria (protocol-level) — high-level, machine-agnostic statements of what it means to conform to the protocol.
7. Extension Model — where and how protocols may be extended, and how extensions affect compatibility.
8. Security Assumptions and Trust Boundaries — high-level requirements (confidentiality, integrity) and attacker model assumptions.
9. Versioning and Compatibility Rules — how versions are named and how compatibility is guaranteed or broken.
10. Impact Analysis — which Adapter_Base and adapter artifacts must be created or updated when this protocol is approved.
11. Decision Record — rationale, alternatives considered, and owners/approvers for the protocol.

Protocol Contracts do NOT include adapter-level operational metadata (such as registration mechanisms, specific metadata fields for a registry, or concrete message serialization). Those concerns belong to Adapter_Base and adapter-level specifications.

## Relationship: Protocol Contract vs Adapter_Base

- Protocol Contract is authoritative for semantics. It says "what" must happen and "what" it means.
- Adapter_Base is the normative template that maps Protocol Contract concepts into an adapter-facing specification. Adapter_Base SHALL:
  - Reference one or more Protocol Contracts that it implements or adapts.
  - Define required metadata fields for adapters (name, version, capabilities, supported-protocol versions).
  - Provide the adapter-level lifecycle hooks and operational expectations in the context of the referenced Protocol Contract.
  - Enumerate adapter-level conformance items derived from protocol-level conformance criteria.

In short: Protocol Contract defines the abstract contract; Adapter_Base defines how adapters document and claim conformance to that contract.

## Conformance and Verification (architecture-only)

Protocol-level conformance SHALL be defined as a set of unambiguous, testable statements (without tests). Examples include:

- Mandatory state transitions that must be supported (e.g., X -> Y on event Z). 
- Required error classes and the minimum acceptable recovery behavior.
- Observable invariants that must hold before/after operations.

Adapter-level conformance (defined in Adapter_Base and adapter specs) SHALL map protocol-level conformance statements to concrete verification items (e.g., specific message patterns, example scenarios, or test vectors). The governance process will determine how conformance artifacts are authored, reviewed, and used in CI.

## Versioning and Evolution

Protocol Contracts MUST declare a version and compatibility policy. Key expectations:

- A Protocol Contract version change is a governance event; the impact and migration path MUST be documented in the Decision Record.
- Backwards-compatible extensions SHOULD be preferred; breaking changes MUST include a deprecation window and a migration strategy.
- Adapter_Base and adapter-level specs MUST declare which protocol contract versions they support.

## Security and Trust Boundaries (high level)

Protocol Contracts MUST document the security assumptions they require. At protocol level this includes:

- Which data categories are considered sensitive in the protocol context.
- High-level authentication/authorization expectations (e.g., mutual authentication required), without mandating specific mechanisms.
- Expected confidentiality and integrity guarantees.

Adapter_Base and adapter specs are responsible for mapping those requirements to concrete operational controls (storage, transmission, secret management) and must reference the protocol-level security expectations.

## Extension Points and Opt-in Features

Protocols SHOULD mark extension points explicitly and specify whether extensions are:

- Safe (do not affect compatibility) or
- Potentially breaking (affect semantics and must be coordinated via governance).

Adapters that implement optional extensions MUST declare them in their Adapter_Base-provided metadata.

## Decision Records and Ownership

Each Protocol Contract SHALL name:

- An owner (person or team responsible for the protocol). 
- A reviewers list. 
- The governance path for changes (reference to Governance: Protocol Change Approval Workflow). 

Decisions and rationale MUST be recorded in the Protocol Contract's Decision Record section.

## Downstream Artifacts and Required Follow-ups

Approval of a Protocol Contract MUST be followed by the creation or update of the following architecture artifacts (spec-only):

- Adapter_Base (update): include references, required metadata fields, and adapter-level conformance mapping.
- Adapter specifications: one per adapter implementing the protocol (GitHub, OpenAI, VSCode, Claude, etc.), written against Adapter_Base template.
- Conformance Specification: protocol-level conformance items elaborated into adapter-level verification templates (spec-only skeletons). 
- Governance updates: protocol versioning and change-approval workflow if not already present.

## Required Review Checklist (for protocol authors)

Authors MUST ensure the Protocol Contract includes or references:

- Explicit Vocabulary references to Glossary.md for all domain terms.
- A state/lifecycle model diagram or textual equivalent.
- A clear error taxonomy and recovery expectations.
- Conformance statements (protocol-level). 
- Owners and reviewers.
- Impact list of downstream artifacts to create/update.

## Open Questions (hidden questions surfaced by this RFC)

- How prescriptive should protocol semantics be regarding timing and performance (left to NFR/Runtime specs)?
- Should Protocol Contracts provide canonical example scenarios (narrative sequences) that adapter specs must include, or should examples live only in adapter-level specs? 
- What minimal metadata must Adapter_Base require to reference a Protocol Contract unambiguously (URI, version, canonical id)?
- Who will own protocol-level conformance verification and how will governance require proof of conformance? 

## Governance and Next Steps (architecture-only)

- Publish RFC-0001 in docs/rfc/RFC-0001.md. 
- Convene an owner and reviewer group to iterate the protocol contract draft. 
- After approval, issue Adapter_Base update RFC to align templates with Protocol Contract decisions. 

## Appendix: Minimal Protocol Contract Template (for authors)

- Title, id, status, date, owners
- Purpose and motivation
- Vocabulary (link to Glossary)
- Abstract operations
- State and lifecycle model
- Error taxonomy and recovery semantics
- Conformance (protocol-level statements)
- Extension points
- Security assumptions
- Versioning/compatibility policy
- Impact analysis (downstream artifacts)
- Decision record

*This RFC is architecture-only. It does not include API definitions, implementation guidance, code snippets, language choices, or runtime instructions.*

Additional Notes:
- RFC-0001 is the root RFC for the Protocol Layer in Shirakami OS.
- All Protocols (e.g., GitHub Protocol, OpenAI Protocol, Shirakami Radio Protocol, VSCode Protocol, Claude Protocol, Guide Protocol) SHALL reference and inherit from RFC-0001.
- Runtime, Adapter, and API layers are subordinate to Protocol Contracts and MUST preserve protocol semantics to maintain compatibility.

Success Criteria:
- When RFC-0001 is approved, Shirakami OS adopts Protocol-First Architecture as a formal principle.
- All future Protocol RFCs MUST reference RFC-0001.
- Runtimes, Adapters, and APIs are considered lower-layer artifacts that implement Protocol semantics and must maintain compatibility unless the protocol is revised.
